# 实测踩坑清单

2026-10-29 全流程跑通（选题→发布草稿箱）时逐条撞到并修掉的坑。跑流水线前扫一遍，能省掉一轮返工。

## 一、发布环节（坑最多）

| 现象 | 原因 | 修法 |
|---|---|---|
| `--title is required` | 把 md 路径当位置参数传给 `wechat-article.ts` | 必须用 `--markdown <path>` |
| 摘要栏被填成 `<!-- image:xxx -->` | ①frontmatter 写了 `digest`，脚本只认 `description` / `summary`（源码 `parseHtmlMeta`）；②取不到摘要时脚本退化抓正文首段，而首段恰好是阶段 3 留下的锚点注释 | 跑 `scripts/publish_prepare.py`，或手工：剥离注释行 + 命令行 `--summary` |
| profile 锁冲突、Chrome 起不来 | 同 profile 只能一个实例，而脚本结束后**故意留着窗口不关** | 重跑前先关掉 `baoyu-skills/chrome-profile` 的那个 Chrome；其他 profile 的窗口互不影响 |
| 粘贴内容错乱、串到别的位置 | 脚本用 PowerShell SendKeys 抢焦点 | 运行期间不要碰鼠标键盘（约 1–3 分钟） |
| API 模式报 40164 | 出口 IP 不在公众号白名单 | `curl ifconfig.me` 查出口；走代理时 IP 会变，改用浏览器模式 |
| **草稿箱里封面缩略图是灰色空块** | `wechat-article.ts` 浏览器模式只填标题/正文/正文图/摘要/存草稿，源码里**没有任何封面设置逻辑**；封面是草稿的独立字段，微信默认灰块 | 发布后在编辑器里手动补：设置封面 → 从正文图片选择 → 选第一张（流水线的封面图恰好都是正文首图）。若要多账号/高频发布，需另行用 CDP 写「设置封面」自动化，当前版本未实现 |

## 二、排版环节

| 现象 | 原因 | 修法 |
|---|---|---|
| `main.ts --output` 无效 | 该脚本根本没有 `--output` 参数 | 产物固定落在输入同目录同名 `.html`，自己 `mv` |
| 图片在 HTML 里是相对路径 | 脚本不做内联 | 本地预览够用；发布时由发布脚本自行上传素材，不受影响 |
| 微信里样式丢失 | 用了自己写的 `<style>` 块 | 用 baoyu 的全内联 HTML |
| **手机端右侧内容被裁掉、看不到** | 微信正文宽度只有 375px，`overflow-x` 不能滚动。`<pre>` 代码块（一行超 ~24 个中文字）和 ≥4 列的表格必然溢出 | 排版前就把这两类改掉：见下方「手机宽度适配」 |

### 手机宽度适配（2026-10-30 新增，必修项）

微信手机端一行只放得下约 24 个中文字，超出部分直接被裁，读者没有任何办法看到。两类内容必须提前改造：

**① 代码块 / 长 prompt → 逐行 `<div>` 卡片**

```html
<div style="background:#F7F8FA;border:1px solid #E8EBEF;border-radius:8px;padding:16px 18px;margin:0 0 18px;font-size:14px;line-height:1.9;color:#2F3A46;">
<div>第一行</div>
<div style="height:8px;"></div>
<div style="padding-left:1.2em;text-indent:-1.2em;">1. 编号行用悬挂缩进</div>
</div>
```

每行一个 `<div>`，宽度自适应、长句自动折行。raw HTML 内联样式 baoyu-md **不清洗**，发布脚本走同一渲染库，微信编辑器也保留。

**② ≥4 列的表格 → 卡片列表**

不要指望表格能压缩。改成每条记录一张卡：标题行加粗 + `字段 · 字段 · <span style="color:...">状态</span>` 小字行 + 引文行，左边条用 `border-left:3px solid` 区分状态颜色。两列表（如「用途/占比」）宽度够，可以保留。

**验收方法（v2.0.0 修正）**：

```bash
chrome.exe --headless=new --disable-gpu --hide-scrollbars \
  --force-device-scale-factor=1 --window-size=500,12000 \
  --screenshot=_v.png file:///<绝对路径>/layout.html
# PIL 测最右墨迹 x（≤468 即无横向溢出），再按 1400-1600px 切段，逐段 ViewImage 查折行/残留标记
```

⚠️ **别再用 `--window-size=375` 当验收依据**：headless Chrome 桌面端有约 500px 的最小窗宽，传 375 时实际版面仍是 ~500px、截图只截了左边 375，于是文字看起来「贴右边缘被裁」——这是假象，v1.2.0 与 v1.3.x 都被它误导过（已发布的 v2 文章复测确认是真无溢出）。流式版面（段落 + `width:100%` 图片）用 500/600px 复核即可放行；真机 375px 验证需要 CDP 移动仿真，本流水线不做。

真正会溢出的是**代码块 / 长 prompt 和 ≥4 列表格**，改造动作照做，只是验收窗宽改成 500。

## 三、配图环节

| 现象 | 原因 | 修法 |
|---|---|---|
| 图里混入乱码文字/字母 | 生图模型对负向提示词遵从不稳定 | 生成后逐张用视觉核验，不合格就重生成 |
| 右下角带「AI 生成」水印 | 生图服务自带 | 纯色底可直接裁掉底部 80px；发布时用公众号自带的「AI 生成声明」做合规标识 |
| manifest 校验不通过 | 锚点与占位符不紧邻，或 ID/尺寸不合规 | 按报错修，不绕过校验 |
| **图与正文关联性弱、被读者嫌「图文无关」** | 生图模型只能出意象图，写不了中文，做不出带文字的流程图/对照表 | 操作型文章改用 **HTML/CSS 手绘信息图 → headless Chrome 截屏**，见下方「信息图方案」 |

### 信息图方案（2026-10-30 新增）

当文章是操作手册/方法论，图必须承担信息（流程图、两栏对照、框架表）时，**不要用生图模型**——它写不了中文，词一定糊成乱码。改用本地渲染：

1. 在 `{ART}/diagrams/*.html` 写页面，固定 `html,body{width:Wpx;height:Hpx}`，深底或浅底按正文主题定
2. 渲染：`chrome.exe --headless=new --force-device-scale-factor=2 --window-size=W,H --screenshot=out.png file:///.../x.html`
3. 逐张 ViewImage 验：文字无乱码/溢出/重叠、列对齐、间距无大片空白（flex 会撑开，需压低画布高度）
4. 源文件保留，改字改色重跑一条命令即可

优点：文字 100% 准确、零积分消耗、可迭代。图注仍建议写清「图与哪一节对应」。

## 四、写作与事实环节

| 现象 | 原因 | 修法 |
|---|---|---|
| 数据看着眼熟但查不到原件 | 自媒体互相转述的「伪数据」 | 按 `fact-check.md` 分级，C 级一律不用 |
| 去 AI 味后字数掉出区间 | 删套话必然掉字 | 补机制说明（不新增事实），别注水 |
| humanizer 后数字变了 | 改写越界 | 改完跑 `scripts/` 里的数字对账（见 fact-check.md 末尾） |

## 五、封面环节（2026-10-30 新增）

| 现象 | 原因 | 修法 |
|---|---|---|
| 封面文字乱码 / 造字 | 用生图服务出封面 | 走阶段 3.5：HTML/CSS 渲染 + 截图 |
| 改一个字就要整图重生成，结果还不可控 | 生图 | 改 HTML 后一条 `render_cover.sh` 重渲 |
| 封面带「AI 生成」水印 | 生图 | HTML 渲染无水印（正文插图才需要裁底部 80px） |
| 草稿箱封面是空的 / 灰块 | 发布脚本不传封面 | 交付 PNG，提醒用户在后台手动「上传本地封面」 |
| 封面和正文首图是同一张 | 图省事复用 | 封面 = 海报（抓眼球），正文首图 = 信息图（讲道理），各做各的 |
| 封面主标题挤成一团 | 直接搬了文章标题 | 缩成 4–6 字 |
| 标签 / 说明句被裁到画布外 | 元素堆太多、字号没算宽 | 按 `cover-style.md` 的排版坑表逐条核对 |

完整规范（文案六要素、配色、双尺寸、排版坑）见 **`references/cover-style.md`**；照片封面见 `references/photo-handling.md`。

## 六、排版脚本重复插图（2026-11-05 新增）

| 现象 | 原因 | 修法 |
|---|---|---|
| `layout.html` 里每张图出现两份 | `baoyu-markdown-to-html` 会读同目录 `image-manifest.json` 自动插一份图，与 markdown 里的 `![]()` 叠加 | ① 排版前临时移开 manifest（`mv image-manifest.json /tmp/` 再跑）；② 生成后按 `src` 去重，每个 src 只留首份；③ **B 类本就不留 manifest**，天然绕开 |
| 同一张图连着两行 markdown 引用 | 替换 `{{IMAGE:...}}` 占位符时，初稿原有的 markdown 图没删 | 替换后 `grep -o '](images/'` 数一遍，与预期张数对齐 |
| 锚点注释 `<!-- image:xxx -->` 混进 HTML | 排版输入没剥锚点 | 排版输入用「只去锚点注释、保留 markdown 图」的变体；或干脆别用锚点 |

发布链路（`publish.md → wechat-article.ts`）本身只渲染 markdown 图一份，**没有这个问题**，别把预览 HTML 的锅算到发布上。

## 七、真实照片与敏感内容（2026-11-06 新增）

| 现象 | 原因 | 修法 |
|---|---|---|
| 中文文件名的照片发布失败 / 路径异常 | `微信图片_2026….jpg` 在 CDP 与脚本路径处理上不稳 | 复制进 `images/` 时统一重命名为 ASCII 短名 |
| 裁剪出来的图和想要的位置完全无关 | 按聊天预览图（810×1080）的坐标去裁原图（3072×4096），差 3.79 倍 | 裁剪前先 `Image.open(p).size`，按比例换算坐标 |
| 弱化裁剪版还是太「完整」 | 主体仍占画面近一半 | 再收一档：只让局部（两簇白毛、爪尖）从边缘入画，其余全是空环境；裁完 ViewImage 验比例 |
| 照片封面底部副标贴左边缘 | `.desc` 是绝对定位，不继承父级 `text-align:center` | 给 `.desc` 自己写 `text-align:center` |
| 敏感照片直接塞进正文后被读者抵触 | 见 `photo-handling.md` 四条判断 | **先给判断、由用户三选一**（不用 / 弱化裁剪 / 原图+提示），别替用户决定 |

B 类完整流程见 **`references/photo-handling.md`**。
