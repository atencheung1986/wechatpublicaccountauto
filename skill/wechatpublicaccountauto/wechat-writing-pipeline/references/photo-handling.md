# 真实照片接入与敏感内容判断

B 类（个人叙事）专属。行业/观点类一般不用真照片。

## 真照片优先于一切手绘

用户提供了本地照片（或说「我有几张真实图片」）→ **真照片全面替代手绘信息图 / 生图**。在个人叙事里，真实感是压倒性的：一张真照片胜过十张信息图，而且能把正文里写到的细节（比如那杯水）当场坐实。

第五篇实测：4 张真照片让两张手绘插画直接作废，其中一张（车底）被真照片顶替，另一张（车底暖光插画）完全弃用。别舍不得已经做好的插画。

## 接入流程

1. 复制到 `{ART}/images/`，**重命名为 ASCII 短名**：`kitten-tire.jpg`、`kitten-feeding.jpg`。中文文件名（微信图片_2026…jpg）会在发布脚本 / CDP 路径处理上惹麻烦
2. 先逐张 ViewImage 看清内容，**再定插入位置**——按叙事顺序排，不按文件名顺序排。每张写清「对应正文哪一节」的 alt
3. 直接写 markdown 图片引用 `![说明](images/xxx.jpg)` 即可。**不必走 `image-manifest.json`**：B 类没有提示词环节，manifest 是 A 类的产物契约
4. 图注可省。叙事文里图注会打断情绪，正文已经说了那是什么
5. 发布链路（`publish.md → wechat-article.ts`）自己会上传本地图片，5 张实测通过，无需额外处理

⚠️ 排完图要核一次：`layout.html` 里 `src="images/..."` 去重后的集合 == 正文引用集合。排版脚本会读同目录 `image-manifest.json` 自动插一份图（见 `pitfalls.md` 二），B 类不留 manifest 正好绕开这个坑。

## 照片封面

用户选照片封面时，用 `templates/cover-photo-feed.html` / `cover-photo-square.html`（B 类首选），渲染同样走 `scripts/render_cover.sh`：

- **feed**：左侧深色文字区（kicker / 主标题 / 副标 / 橙线 / 三标签）+ 右侧照片区。用 `background-position` 把主体调到可见位置，左侧压一层深色渐变做过渡
- **square**：照片全幅铺底 + 上下渐变遮罩，标题在上、副标在下。**文字必须 `text-align:center`**（绝对定位元素不继承父级居中，忘了会贴左边缘）
- 选一张主体清晰、正脸 / 全身可见的照片做底；横版方图两个尺寸都要出
- **保留原设计版封面文件**（`cover-feed.png` / `cover-square.png`），用户随时能换回

## 敏感照片：先给判断，再让用户定

遇到死亡、伤病、血腥、隐私类照片，**不要默默塞进正文**。第五篇的图 4（小猫遗体）就是这么处理的：先讲清四条理由，再由用户三选一。

| 理由 | 说明 |
|---|---|
| **传播链断裂** | 读者转发前会犹豫「别人刷到会不会不舒服」。公众号没有算法推荐，全靠转发，这一跳断了文章就死了 |
| **平台灰区** | 「引起不适」类内容可被举报，判定尺度不在自己手里，轻则删文、重则影响账号 |
| **关闭想象** | 文字 + 前面几张「活着的她」已经让读者各自有画面；照片摆出来，文章从「纪念」滑向「展示死亡」，同情会变成抵触 |
| **私人 vs 公开** | 这张照片对用户的意义是私人的，值得留着，但不等于适合公开发布 |

**给三个选项**：不用（推荐）/ 裁剪弱化版 / 原图 + 阅读提示。用户选了原图也要如实执行，别反复劝。

### 弱化裁剪做法

目标：画面大部分是空环境，主体只从边缘入画一小部分——**看得懂，但不直接**。

1. 裁掉头部和主体全貌，只留局部（两簇白毛、一个爪尖）+ 大面积地面 / 环境线
2. ⚠️ **PIL 裁剪前必须核对原图真实尺寸**：聊天预览图（810×1080）和原图（3072×4096）差 3.79 倍，按预览坐标裁会裁到完全无关的区域。先 `Image.open(p).size`
3. 裁完 ViewImage 验一次比例；还太完整就再收一档（第五篇收了两档才合格）
4. 原图保留在 `images/` 不删除，只是不引用
5. 放在文中「然后我看见了」这类句子**之后**，前面不放任何提示文字

## 一个 related 的坑

照片版正文里，**真照片和 HTML 告示卡可以共存**：第五篇 4 张真照片 + 1 张「上车前三个动作」告示卡。告示卡是行动指令，不是叙事，做成卡片反而把「故事」和「呼吁」在视觉上分开了——这个搭配值得复用。
